=== Slide 2 ===
The Problem — and Our Solution
The Problem
Students with accessibility needs juggle 5+ disconnected tools — screen reader, captioner, translator, PDF reader — none aware of each other. Campuses lack a unified, real-time accessibility layer.
The Solution
Saathi is a single Progressive Web App powered by one multimodal AI agent. Set your profile once — visual, hearing, cognitive, motor, or language — and any input is routed to the right pipeline, returned in the format you need.

=== Slide 5 ===
Technical Strategy: Methodology
Core Approach: PAMR
The Personalisation-Aware Modality Router is a lightweight routing layer between user input and the AI agent. It reads the user's saved profile and input type, then directs each request to the correct pipeline and formats output in the accessible modality that profile requires.

Modular architecture means each feature can be built and tested independently — critical for hackathon timelines.
=== Slide 6 ===
Implementation Flow





Every input — regardless of type — is processed end-to-end in under 3 seconds, delivering accessible output in the user's preferred modality without any manual routing.

=== Slide 10 ===
Why This Idea May Fail
AI Accuracy Limits
Vision and speech models can misread in poor lighting, background noise, or with accented speech — a core reliability risk.
Narrow MVP Scope
True accessibility (e.g., full sign language support) needs far more than a hackathon build — MVP covers only a subset.
Adoption Inertia
Students already using Google Live Transcribe or Speechify may be slow to switch to a new tool.
API Dependency
Free-tier rate limits or provider downtime directly affect reliability during critical demo moments.
Institutional Buy-In Needed
Lecture-level captioning requires faculty cooperation and mic access — outside the team's direct control.
